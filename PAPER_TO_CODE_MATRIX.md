# Paper-to-code matrix

This matrix distinguishes executable semantics, registry records and released
evidence. The root source-data verifier checks archive hashes, closed manifest
and checksum path sets, CSV counts and shapes, and the declared QC status. The
platform estimators consume a separate canonical long-form record contract;
they do not ingest the Zenodo v4 experiment-specific wide CSVs directly.

## Statistical inference

| Platform | Executable estimator | Enforced independent unit |
|---|---|---|
| Satellite | `scripts/summarize_results.py --platform satellite --estimator run_first_student_t` | Ten equal-weight training-run means; two-sided Student-t summary intervals and paired Student-t contrasts, df=9 |
| UAV | `scripts/summarize_results.py --platform uav --estimator run_first_hierarchical_bootstrap` | Five independent training runs; equal-weight run means with the nested-within-run hierarchical bootstrap |

`configs/ANALYSIS_PLAN_TEMPLATE.json` records both contracts but intentionally
contains no analysis items. Copy and populate it for a canonical record set.
Each invocation
accepts one platform only and rejects disagreement among the CLI estimator,
analysis plan and input records.

## Central claim and controller-facing interface

| Manuscript object | Demonstration or implementation | Root release check |
|---|---|---|
| Controller-facing interface `(D, Stage, S)` | `src/controller_facing_state/demo.py`; satellite interface and policy modules under `code/satellite`; UAV state and policy modules under `code/uav/uav_cfs` | `verify-config` checks the fixed role order and weights; `experiments --id EXP2` exposes the registered descriptor, staging and score-map levels |
| Persistent candidate and resource identity | Satellite `ControlObservation` validation in the demo; platform graph and state modules | The root verifier checks archive structure, not candidate-key semantics; candidate and event keys remain available in the released tables for analysis |
| Hard feasibility before ranking | The demo executes the satellite and UAV hard-mask policies | `verify-config` checks both platform hard-mask settings and selected controller constants |
| Proposal versus executed action | Satellite policy output and one UAV environment execution step are exercised in the demo | Proposal and execution records can be analysed from the released tables; no root command reconstructs missing trajectories |
| Feedback-coupled next state | Platform environment transition modules; one UAV transition is executed in the demo | The archive provides observed run records; simulator states are not regenerated by `verify-source-data` |

## Extended experiments

| Experiment | Registered design | What the Zenodo v4 tables support | What still requires original assets |
|---|---|---|---|
| FCT-CL core factorial | Snapshot/Intensity--Flow by MLP/PhysiCK, ten independent runs and 30 held-out episodes per cell | Cross-interface and cross-operator summaries from the core source-data tables | Training streams, checkpoint tensors and full retraining |
| EXP1 checkpoint landscape | Two contracts, 20 paired seeds, two models, 50 checkpoints, five selection rules | Checkpoint selection, equivalence gates, near-tie strata, nested reassociation-window counts and summaries | Checkpoint tensors and state-level model evaluation |

| EXP3 decision-aware objective | MLP/PhysiCK by predictive/decision-aware objective, 20 paired seeds per arm | Arm summaries, interaction contrasts and the declared four-arm rare-event correction | Training streams, checkpoint tensors and full retraining |
| EXP4 external environment | Two models across 12 paired traces | Published numerical summaries and count/exposure checks | Environment identity, source/version, trace split and field mapping are not recorded, so the original evaluation cannot be rerun from this release |
| EXP5 PhysiCK ablation | Ordered MLP, dynamic mixture, unprojected PhysiCK and projected PhysiCK sequence | Paired summaries, predictive guardrails, diagnostic contrasts and projection activity | Checkpoint tensors and new training runs |

## Root entry points

| Task | Command |
|---|---|
| Run semantic demonstration | `./run_demo.sh` |
| List registered experiments | `python -m controller_facing_state.cli experiments` |
| Inspect one design | `python -m controller_facing_state.cli experiments --id EXP1` |
| Check bundled configuration | `python -m controller_facing_state.cli verify-config` |
| Audit Table S11 identities | `python -m controller_facing_state.cli audit-model-identities` |
| Check Zenodo records | `python -m controller_facing_state.cli verify-source-data --source-data SOURCE_DATA_ROOT` |
| Apply a platform estimator to canonical records | `python scripts/summarize_results.py --platform PLATFORM --estimator ESTIMATOR ...` |
| Run release tests | `./run_tests.sh` |
| Check configuration and optional source data together | `./verify_paper_contract.sh [SOURCE_DATA_ROOT]` |

The Zenodo run and checkpoint files are the quantitative authority for the
reported records. The experiment registry is the machine-readable design
record exposed by this release. Once software version 2.0.0 is uploaded, its
new release tag and immutable commit are the software authority. Commit
`d096a2020649d360dfffc860309a510734ea6033` remains the upstream pre-v2 lineage
and does not contain the version 2.0.0 additions.
